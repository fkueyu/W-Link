# 系统架构设计 (Architecture Design)

本文档旨在阐述 W-Link 的核心架构设计理念与技术选型。作为一款面向 IoT 设备的现代化控制终端，W-Link 在设计上始终贯彻**“极简”、“防御性”**与**“响应优先”**的核心原则。

## 1. 核心技术栈

- **框架**: Flutter (Dart 3.0+ 强类型、空安全、模式匹配)
- **状态管理**: Riverpod 2.0+ (配合 `riverpod_generator` 实现完全的类型安全)
- **网络通信**: 原生 `http` 包 (HTTP 1.1 Keep-Alive 维持长连接) + `multicast_dns` (设备发现)
- **本地持久化**: `shared_preferences` (轻量级配置存储)

## 2. 架构分层

整个项目采用基于领域驱动设计（DDD）的简化版 **Feature-First (按功能模块分层)** 架构。

```text
lib/
├── core/             # 核心层：路由、主题、网络基础客户端、工具类、常量定义
├── models/           # 数据层：WLED 官方 API 的 JSON 映射实体类（基于 json_serializable）
├── services/         # 服务层：与硬件或底层系统交互的具体实现 (mDNS 扫描, HTTP 通信, 本地存储)
├── providers/        # 状态层：Riverpod 逻辑容器，连接 UI 与 Services，处理业务状态机
└── screens/          # 表现层：UI 界面、Glassmorphism 组件、动画包装
```

## 3. 核心机制设计

### 3.1 设备发现机制 (Zero Config)

IoT 设备的传统痛点是需要用户手动输入 IP。W-Link 通过底层的 `mDNS` (多播 DNS) 实现了零配置发现。

1. App 启动时，`MDNSService` 在局域网内广播查询 `_http._tcp.local` 的 WLED 节点。
2. 发现设备后，立即触发轻量级的 HTTP GET `/json/info` 获取设备特征（如 MAC 地址、设备名称、是否在线）。
3. 状态层 `devicesProvider` 维护一个去重的可用设备列表，供 UI 实时展示。

### 3.2 乐观 UI 与防抖 (Optimistic UI & Debounce)

**这是 W-Link 交互流畅的核心。** 用户在滑动调色盘或亮度滑块时，若每次都等待 HTTP 响应，UI 会出现严重的顿挫感，并且极易打满 ESP8266/ESP32 的 TCP 连接数导致芯片崩溃。

- **乐观更新 (Optimistic Update)**:
  当用户触发状态改变（如点击开关、改变颜色）时，状态管理层立即更新本地 UI 状态，用户瞬间得到反馈。随后在后台异步发起网络请求，若请求失败，则将 UI 回滚到上一状态，并抛出无感知的 Toast 提示。
- **防抖与节流 (Debounce / Throttle)**:
  对高频滑块事件采用 `Debounce` 策略（例如 200ms）。在用户连续滑动的过程中，UI 实时重绘响应滑块位置，但底层网络层通过节流器阻断发送，直到用户停止滑动才会将最终的 JSON 状态 POST 给 WLED。

### 3.3 防御性网络通信 (Defensive Networking)

由于局域网环境的不确定性（如 Wi-Fi 信号衰减、IoT 芯片处理能力弱），网络请求随时可能超时或断开。

- **HTTP Keep-Alive**: 通过复用底层的 TCP 连接，省去了每次请求都需要三次握手的开销，极大降低了控制指令的延迟。
- **超时与重试**: 在 `core/http_client` 中封装了统一的异常捕获机制，捕获 `SocketException` 和 `TimeoutException`。采用指数退避（Exponential Backoff）策略进行静默重试。
- **离线降级处理**: 当 WLED 设备被拔电或离线时，UI 会监听到心跳失败，优雅地将该设备卡片置灰并显示离线状态，而不是导致 App 卡死或崩溃。

## 4. UI/UX 设计理念

- **Glassmorphism (玻璃拟态)**: 利用底层的 `BackdropFilter` 实现高斯模糊，搭配半透明的边框和阴影，营造高级感。
- **声明式微动画**: 使用 `flutter_animate` 将枯燥的状态切换（如开关打开）封装成自然过渡的缩放、弹性物理动画。

## 5. 扩展性思考

目前架构为单端通信模式。未来若要实现音乐律动（Sound Reactive）的低延迟同步控制，可平滑地在 Service 层引入基于 UDP 的 E1.31 / WLED Realtime 协议支持，无需重构现有 UI 与状态层逻辑。
